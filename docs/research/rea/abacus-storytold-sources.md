## Что подтверждено документацией

Abacus AI Agent (бывший DeepAgent) — облачный агент для создания приложений, исследований, документов и автоматизации. Официальное описание разделяет модели, инструменты, интеграции, браузер/рабочий стол и параллельные задачи. Есть выбор effort — уровня затрат и усилий модели. Это описание продукта, не доказательство внутреннего алгоритма маршрутизации. [Обзор](https://abacus.ai/help/chatllm-ai-super-assistant/deepagent).

Для приложений описаны preview, история версий, контрольные точки, откат и отдельное действие Deploy; управление базой, авторизацией и доменами. В этой же инструкции старое ограничение на существующие кодовые базы расходится с новым общим обзором, обещающим работу с ними: точные границы без запуска не установлены. [Apps](https://abacus.ai/help/chatllm-ai-super-assistant/deepagent-apps).

Коннекторы разделены на пользовательские (действия от имени пользователя, чтение по запросу) и организационные (загрузка данных для общих моделей). MCP — дополнительный канал интеграций. [Connectors](https://api.abacus.ai/help/connectors/introduction).

Автоматизация запускается по расписанию, вручную или событию. Для самоулучшения заявлены фиксированная метрика, исходное измерение, одна правка за проход и независимая оценка; при застое возможна пауза. Это полезная продуктовая модель, но качество такого цикла нами не испытано. [Tasks](https://abacus.ai/help/chatllm-ai-super-assistant/self-improving-tasks-and-agents).

## Что именно есть у storytold

`storytold` — организация ArtCraft. Под задачу подходит [craft-anything](https://github.com/storytold/craft-anything), а не весь набор редакторов организации. Это самостоятельный Rust-инструмент изучения и воспроизведения ПО с CLI/MCP и циклом Study → Build → Check → Ready. Он не является исходниками Abacus.

README различает Clean room (наблюдаемое поведение и внешний вид) и Deep (чтение внутренних файлов/JavaScript). Clean room не является системной песочницей. Состояние проекта — ранняя alpha; основной builder — установленный Claude Code. Лицензии перечислены как Apache-2.0/MIT; перед переносом конкретного файла необходимо проверить его лицензию и NOTICE. [README](https://github.com/storytold/craft-anything).

Для исследования веб-продукта каталог предлагает `web_site_open`, `web_site_capture`, `web_page_states_capture`, `web_walkthrough_record/check`, `web_snapshots_compare`; для Deep-анализа — `web_page_js_analyze`, `web_page_watch`, `web_modules_trace`. Это документированные инструменты, в данной сессии они не запускались. [Каталог](https://github.com/storytold/craft-anything/blob/main/docs/tools.md).

Журнал статуса описывает сравнение страниц на нескольких ширинах и сохранение доказательств/неизвестных фактов. Codex-адаптер проверялся с имитацией модельного сервера; реальная сборка через аккаунт Codex ещё не подтверждена. Автоматический процент визуального сходства не доказывает эквивалентность поведения или бэкенда. [STATUS](https://github.com/storytold/craft-anything/blob/main/docs/STATUS.md).

## Предложения для нашего проекта — проектные решения

| Идея | Применение | Очередь |
|---|---|---|
| Версии результата рядом с чатом | Улучшать существующую панель Artifact: версия, источник, экспорт, ясный статический режим | Ближайший небольшой срез |
| Проверяемые этапы работы | Показывать реальные состояния запроса/инструмента и результат проверки, не выдуманный процент выполнения | После сверки текущего UI |
| Отдельные разрешения интеграций | Позже показывать, какие данные и действия доступны каждому подключению | После P0 |
| Независимая проверка результата | Сравнивать синтетические сценарии и снимки своего UI с явно заданными критериями | Инструменты разработки |
| Облачный компьютер, browser use, schedules | Потребуют отдельного исполнителя, лимитов, возобновления и прав | Отдельная агентная стадия |

Craft Anything разумнее использовать внешним исследовательским инструментом: снять публичные экраны и состояния → сформулировать собственный UX-контракт → реализовать выборочно в Tauri → проверить на синтетических данных. Встраивать весь движок в клиент для этого не требуется.

`spec.md` относит агентные инструменты к P2, но поздние записи `checks.md` уже описывают экспериментальные `calculate`/`search_project` (тикеты 16/17) с незавершённой живой проверкой. Наличие этих записей не означает готовый аналог DeepAgent и не меняет границы P0 автоматически.

Не установлены: устройство закрытого оркестратора Abacus, системные промпты, схема хранения, реализация облачной изоляции и биллинга, приватные API, поведение авторизованных экранов. Публичная документация позволяет восстановить концепцию продукта, но не эти внутренности.

## Рабочая схема продукта и перенос в клиент

Следующая схема — вывод из документации и статических признаков, не восстановленный внутренний call graph:

`Запрос → выбор режима/модели → план и вызовы инструментов → среда выполнения / коннекторы / браузер → файлы и preview → проверка → версия / экспорт / публикация`.

Для нашего приложения соответствие такое:

| Слой | Что уже есть в исходниках | Разумное продолжение |
|---|---|---|
| Чат и контекст | React UI, Rust HTTP/SSE, сохранение попыток и контекста | Сохранить текущие границы ответственности |
| План работы | `AgentBoard`, план/очередь/уточнения в SQLite | Связать отображение с реальными событиями выполнения, не выдавать ручной список за автономный планировщик |
| Инструменты | `calculate`, ограниченный `search_project`, потоковые `tool_calls` в `lib.rs` | Сначала проверить сквозной цикл в приложении; это уже не только будущая идея |
| Результат | `ArtifactPanel`, версии, Code, экспорт, статический Preview | Проверить существующий сценарий версий; затем добавить видимый результат проверки и связь с попыткой, если их не хватает |
| Исполнитель команд | Тикет 18 заблокирован: положительный тест macOS sandbox не прошёл | Не открывать shell ради повторения возможностей Abacus |
| Интерактивный viewer | Тикет 23 зависит от отрицательных проверок и Windows | Статический Preview до выполнения критериев |
| Облачные задания | Не часть локального P0 | Отдельное архитектурное решение, сервер и операционные расходы |

### Предлагаемый ближайший проверяемый срез

Одна задача с текстовым/HTML-результатом: видна попытка → пользователь открывает Code/статический Preview → выбирает старую версию → экспортирует именно её → после перезапуска версии сохранны. При обрыве генерации результат явно частичный; старая версия не заменяется. Сначала проверить имеющуюся реализацию, затем менять только найденные пробелы. Это предложение, не выполненная разработка.

### Как использовать Craft Anything предметно

1. Выбрать три сценария: начало задачи, просмотр результата, переход между версиями. Для авторизованной части нужен отдельный тестовый аккаунт и синтетическая задача; текущая сессия остановилась на регистрации.
2. Через `web_page_states_capture` и `web_walkthrough_record` собрать состояния и переходы; через `web_walkthrough_check` проверить повторяемость. Сохранять ошибки и ограничения рядом с удачными проходами.
3. Записать собственные требования к поведению. Использовать `web_page_js_analyze`/`web_modules_trace` только для оставшихся вопросов о публичном клиентском коде; они не извлекут облачную логику.
4. Реализовать выбранный сценарий в существующих React/Rust-компонентах. `web_snapshots_compare` поможет сравнить состояния браузерного UI, но не заменит macOS WebKit/IPC-проверки нативного клиента.
