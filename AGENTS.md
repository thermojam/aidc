## Безопасность и данные

- Никаких автоматических повторов платного POST при неизвестном результате. Не считай обрыв до первого токена доказательством, что запрос не принят. Отсутствие `usage` означает «неизвестно».
- Ключ SimpleClaw держи в системном хранилище и используй только из Rust. Не передавай его в JS, SQLite, логи или Artifacts. Не делай универсальную команду `get_api_key`.
- Локальный `.env` содержит адрес API и два ключа для ручных проверок; это не источник ключа для приложения. Не выводи значения переменных или содержимое `.env` в отчёт, код, логи и аргументы процессов. Пользователь разрешил проверочные запросы с суммарным лимитом 100 ₽ на оба ключа; считай фактический расход неизвестным без подтверждения сервера. После двух ответов `503 UPSTREAM_USAGE_UNCERTAIN` повторять тот же POST автоматически или вручную без новой причины не нужно. Приложение по-прежнему должно получать ключ только из системного хранилища через Rust.
- В Tauri собственные `invoke_handler` команды по умолчанию доступны всем окнам и webview. Включи их в `AppManifest::commands`, разрешай поимённо только нужному окну и проверяй отрицательный сценарий для недоверенного viewer.
- Не читай личные чаты, профиль, cookies или ключи пользователя для исследования. Для тестов используй синтетические данные и отдельный профиль. Не делай платные вызовы без отдельного разрешения на конкретные расходы.
- Не исполняй код модели в главном окне. Интерактивные Artifacts допускаются только после проверок из `spec.md` на WebView2 и WebKit; до этого используй Code и статический Preview.

## Реализация и проверка

- Перед нетривиальной работой сформулируй допущения и проверяемый результат. Выбери простейшее решение, которое закрывает текущий срез. Не добавляй зависимости и слои «на будущее».
- Меняй только относящиеся к задаче файлы, сохраняй чужие незакоммиченные изменения. Не создавай worktree без запроса пользователя.
- Для потоков проверяй разрезанный UTF-8/JSON, несколько событий в одном чанке, обрыв без конца, отмену, отсутствие дублей и восстановление частичного ответа. Для БД проверяй миграции, ветки, незавершённую попытку и резервную копию по мере реализации этих функций.
- Запускай существующие тесты, линтер, проверку типов и сборку по мере появления проекта. Не создавай тестовую инфраструктуру только ради отчёта. Сообщай, что реально запускалось, на какой ОС и что осталось непроверенным.
- Обновляй `docs/research/rea/checks.md` при снятии открытых вопросов и фиксируй новый контракт или решение в `spec.md`. Не заменяй измерения оценками.
